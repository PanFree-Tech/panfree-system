## AUD-005 - RLS admin desde user_metadata

**Severidad:** Critica
**Archivo original:** migrations/create_configuracion_y_usuarios.sql:59-82
**Estado:** Cerrado (PR #49)
**Estado en DB:** ya estaba corregido antes del PR (usaba is_admin())

### Problema

Las politicas de configuracion_sitio y usuarios leian el rol desde:
- auth.jwt() -> user_metadata ->> role
- auth.jwt() -> raw_user_meta_data ->> role
- auth.jwt() -> app_metadata ->> role

user_metadata y raw_user_meta_data son editables por el usuario via supabase.auth.updateUser(). Cualquier cuenta podia auto-promoverse a admin y modificar configuracion del sitio y gestionar usuarios.

### Solucion

- La funcion public.is_admin() (SECURITY DEFINER, STABLE) consulta clientes.role WHERE user_id = auth.uid().
- El rol real vive en la tabla clientes, no en JWT metadata.
- El SQL versionado en migrations/ tenia el coalesce viejo (aunque la DB ya estaba bien). Se agrego la migracion 2026-10-19-s41-aud-005-007-rls-admin.sql para que el estado sea reproducible.
- REVOKE EXECUTE ON FUNCTION public.is_admin() FROM anon, authenticated, public.

### Verificacion

- pg_policies confirma que configuracion_sitio y usuarios usan is_admin() OR service_role.
- Middleware.js lee user.app_metadata.role (ADR-002, correcto en codigo).
- is_admin() fue auditada: solo lee clientes.role, no JWT metadata.

## AUD-006 - RLS permisiva en fidelizacion

**Severidad:** Alta
**Archivo original:** migrations/add_dipticos_y_gamificacion.sql:133-173
**Estado:** Cerrado (PR #51)

### Problema

Multiples politicas USING(true) y WITH CHECK(true) en:
- codigos_dipticos: SELECT USING(true) permitia enumerar todos los codigos no canjeados. UPDATE USING(true) permitia marcarlos como canjeados.
- canjes_dipticos: SELECT USING(true) filtraba datos personales. INSERT WITH CHECK(true) permitia inflar puntos.
- premios: ALL USING(auth.role()='authenticated') permitia a cualquier logueado gestionar premios.
- canjes_premios: SELECT USING(true) filtraba datos. Ademas tenia un bug de join (auth.uid() = cliente_id en vez de user_id).

Adicionalmente, el flujo de canje en src/lib/dipticos.js hacia 3 operaciones HTTP separadas (INSERT + UPDATE + UPDATE), lo cual no era atomico y tenia race conditions. El cliente podia auto-asignarse puntos.

### Solucion

**Migracion SQL 2026-10-19-s42-aud-006-rls-fidelizacion.sql:**
- ALTER TABLE codigos_dipticos ADD COLUMN puntos_ganados integer DEFAULT 100.
- DROP POLICY "Lectura publica de codigos dipticos".
- Fix de canjes_premios: SELECT e INSERT usan cliente_id IN (SELECT id FROM clientes WHERE user_id = auth.uid()).
- CREATE FUNCTION validar_codigo_diptico(p_codigo text) SECURITY DEFINER.
- CREATE FUNCTION canjear_diptico(p_codigo text) SECURITY DEFINER con FOR UPDATE (atomico).
- CREATE FUNCTION canjear_premio(p_premio_id uuid) SECURITY DEFINER con FOR UPDATE (atomico).
- DROP TRIGGER trigger_sumar_puntos_diptico (el RPC ya suma, evita doble).
- REVOKE EXECUTE FROM anon, GRANT TO authenticated en los 3 RPCs.

**Frontend src/lib/dipticos.js reescrito:**
- canjearCodigo() usa supabase.rpc('canjear_diptico').
- canjearPremio() usa supabase.rpc('canjear_premio').
- validarCodigo() usa supabase.rpc('validar_codigo_diptico').
- Eliminado puntos_ganados hardcoded en el cliente.

### Verificacion

- pg_policies confirma que codigos_dipticos solo tiene "Admin y service_role acceso codigos_dipticos".
- pg_policies confirma que canjes_premios tiene 5 politicas con el join correcto.
- information_schema.triggers confirma que trigger_sumar_puntos_diptico ya no existe.
- pg_proc confirma los 3 RPCs.
- Select-String confirma que solo dipticos.js usa canjes_dipticos (no hay otros flujos afectados).

## AUD-007 - email_logs accesible por authenticated

**Severidad:** Alta
**Archivo original:** migrations/create_email_logs.sql:25-39
**Estado:** Cerrado (PR #49)

### Problema

La politica "Admin and Service Role full access on email_logs" usaba:
  USING (auth.role() = 'service_role' OR auth.role() = 'authenticated')

Cualquier usuario logueado podia leer todos los correos enviados via Resend (to_email, subject, body_html, metadata). Fuga masiva de PII.

Ademas habia una segunda politica "Service role full access on email_logs" con USING(true) WITH CHECK(true), que anulaba la anterior. Cualquier rol (incluso anon) podia leer todos los correos.

### Solucion

- DROP POLICY de las 2 politicas viejas.
- CREATE POLICY "Admin email_logs" con is_admin() solamente.
- service_role bypassa RLS por defecto, no necesita politica.

### Verificacion

- pg_policies confirma que email_logs solo tiene "Admin email_logs" con is_admin().
- Test en produccion: usuario no-admin intenta SELECT -> 0 filas. anon -> 0 filas.

## AUD-008 - Middleware con getSession (falso positivo)

**Severidad:** Discrepancia (no es vulnerabilidad)
**Archivo:** src/middleware.js
**Estado:** Cerrado como falso positivo (sin PR)

### Problema reportado

El codigo publico en GitHub parecia mostrar el fallback a supabase.auth.getSession() en el middleware.

### Diagnostico

git show HEAD:src/middleware.js confirma que el archivo en main usa exclusivamente supabase.auth.getUser() y user.app_metadata.role. No hay getSession() en el codigo.

git diff HEAD -- src/middleware.js esta vacio (working tree == HEAD).

git log --all --oneline -- src/middleware.js confirma que el fix de S37 esta en main (commit dd4d9d49 fix(auth): leer rol solo desde app_metadata en middleware).

### Conclusion

El reporte original fue por cache de GitHub (CDN) o por una pestana del navegador con el archivo abierto desde antes del merge. El codigo en main es correcto.

## AUD-009 - Fail-open en notificar-pedido

**Severidad:** Alta
**Archivo original:** src/app/api/notificar-pedido/route.js:50-68
**Estado:** Cerrado (PR #50)

### Problema

El endpoint verificaba el token solo si habia tokens configurados:

  if (validTokens.length > 0 && token && !validTokens.includes(token)) {
    return NextResponse.json({ error: 'No autorizado' }, { status: 401 })
  }

Si validTokens estaba vacio (env vars no creadas), o si el token era undefined (header ausente), la ejecucion continuaba. Fail-open.

En produccion, N8N_WEBHOOK_TOKEN y NEXT_PUBLIC_API_TOKEN no estaban configurados, asi que el endpoint estaba 100% abierto. Cualquiera podia disparar emails de confirmacion falsos y crear filas en notificaciones_admin.

### Solucion

- Nuevo helper src/lib/api-auth.js con requireAuth(req, { requireAdmin }).
- Modo 1: API_TOKEN compartido (server-to-server).
- Modo 2: JWT de Supabase validado con getUser() + chequeo de clientes.role = 'admin' (si requireAdmin).
- Sin header Authorization -> 401.
- token invalido -> 401.
- role no admin (si requireAdmin) -> 403.

En notificar-pedido:
  const auth = await requireAuth(req, { requireAdmin: false })
  if (!auth.ok) return auth.response

requireAdmin: false porque el caller crear-pedido es el checkout (puede ejecutarse sin usuario logueado, con API_TOKEN).

### Verificacion

- Test en produccion: POST /api/notificar-pedido sin header -> 401 "No autorizado: falta header Authorization".
- Test en produccion: POST /api/notificar-pedido con JWT admin -> 200.
- Test en produccion: POST /api/notificar-pedido con API_TOKEN -> 200 (crear-pedido lo usa).

## AUD-010 - push-notificar sin auth

**Severidad:** Critica
**Archivo original:** src/app/api/push-notificar/route.js:56-76, 109-170
**Estado:** Cerrado (PR #50)

### Problema

El endpoint no tenia ninguna auth. Usaba SUPABASE_SERVICE_ROLE_KEY si estaba presente, bypasseando RLS. El else if (sendToAdmins || !targetUserId) era siempre verdadero cuando no habia targetUserId, disparando difusion general. Ademas tenia un fallback .limit(50) a push_subscriptions completa si no encontraba admins suscritos.

Cualquiera con la URL podia difundir push a todos los suscriptores (50 dispositivos).

### Solucion

- const auth = await requireAuth(request, { requireAdmin: true }) al inicio del POST.
- Eliminado el fallback .limit(50).
- else if (sendToAdmins === true) en vez de sendToAdmins || !targetUserId.
- Si no hay admin ni user_id -> 400 (antes difundia).

### Verificacion

- Test en produccion: POST /api/push-notificar sin header -> 401.
- Test en produccion: POST /api/push-notificar con JWT admin -> 200.

## AUD-011 - puntos_fidelidad manipulable (nuevo)

**Severidad:** Critica
**Archivo:** politica RLS clientes_update_policy
**Estado:** Cerrado (PR #47)
**Origen:** detectado durante el analisis de AUD-006, no estaba en la auditoria original

### Problema

clientes_update_policy permitia UPDATE total de la fila del cliente:

  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid())

Cualquier usuario logueado podia hacer:
  await supabase.from('clientes')
    .update({ puntos_fidelidad: 999999, nivel_cliente: 'vip' })
    .eq('id', 'su-propio-id')

Y auto-asignarse puntos y nivel VIP. Esto anulaba cualquier otra proteccion de fidelizacion.

### Solucion

- DROP POLICY clientes_update_policy.
- CREATE POLICY clientes_update_policy con WITH CHECK que valida que puntos_fidelidad y nivel_cliente NO cambian:
  WITH CHECK (
    user_id = (SELECT auth.uid())
    AND puntos_fidelidad = (SELECT puntos_fidelidad FROM public.clientes WHERE user_id = (SELECT auth.uid()))
    AND nivel_cliente = (SELECT nivel_cliente FROM public.clientes WHERE user_id = (SELECT auth.uid()))
  )

Los campos puntos_fidelidad y nivel_cliente solo los modifican:
- Trigger sumar_puntos_diptico (SECURITY DEFINER, bypass RLS, aunque ahora eliminado en favor del RPC).
- RPC canjear_diptico / canjear_premio (SECURITY DEFINER, bypass RLS).
- service_role (backend/admin, bypass RLS).

### Verificacion

- pg_policies confirma la nueva politica con el WITH CHECK extendido.
- Test en produccion: usuario logueado intenta update({puntos_fidelidad: 999999}) -> error "new row violates row-level security policy".
- Test en produccion: usuario logueado edita nombre_completo o telefono -> OK.
